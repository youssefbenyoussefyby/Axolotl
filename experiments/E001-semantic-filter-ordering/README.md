This is the cheap first experiment that [RESEARCH.md §6](../../docs/research/RESEARCH.md#6-constraints-and-open-decisions)
asks for. It needs only the P4 operator framework, not P7 vector search or the P8
optimizer.

## Question

A query mixes ordinary relational predicates (comparisons costing nanoseconds) with
one *semantic* predicate evaluated by a language model (costing hundreds of
milliseconds and real money). How much does the predicate's position in the filter
chain matter, and does a simple selectivity × cost ordering rule capture most of the
benefit?

## Hypothesis

H1: Evaluating the semantic predicate after the relational predicates reduces model
calls per query in proportion to the relational predicates' combined selectivity, with
identical result rows. For relational selectivity ≤ 0.2, that is a ≥ 5× reduction.

H2: Ranking predicates by `cost / (1 − selectivity)` (the classic rank ordering for
expensive predicates) picks the cheapest order on ≥ 90% of the generated queries.

H1 is close to an identity, and stating it plainly is deliberate: it checks that the
harness counts correctly before any less obvious claim (H2, and later model-assisted
placement) is trusted.

## Baselines

- **B0 — semantic first:** the semantic predicate is evaluated on every row, then the
  cheap predicates.
- **B1 — written order:** predicates are evaluated in the order the query text gives.
- **B2 — oracle order:** for each query, the cheapest order found by exhaustively
  evaluating every permutation on the data. This is the upper bound.

## Metrics

| Metric | Definition | How measured |
|--------|------------|--------------|
| Model calls / query | Number of semantic-predicate evaluations | Counter in the operator |
| Latency | Wall-clock per query, median and p95 over 5 runs | `steady_clock` around `Next()` loop |
| Result equality | Same multiset of rows as B0 | Row-set comparison (must be 100%) |
| Ordering regret | (cost of chosen order − cost of B2) / cost of B2 | Computed from call counts × measured per-call cost |

## Data

- A synthetic product-review table `reviews(id INT, rating INT, year INT, text VARCHAR)`,
  generated by a committed script with a fixed seed, 10k rows.
- `text` drawn from a small labelled pool so the semantic predicate ("the review
  complains about shipping") has ground-truth labels.
- Model responses cached by prompt hash, so reruns are free and deterministic.
  A deterministic **mock model** that reads the labels is used first. It separates
  harness correctness from model behaviour.

## Procedure

1. Implement a `SemanticFilter` operator (maintainer's task) with a pluggable
   `Predicate` backend: mock (label lookup with simulated latency) and real (hosted
   model, cached).
2. Generate 50 queries with 1–3 cheap predicates of controlled selectivity
   (0.01, 0.05, 0.2, 0.5, 1.0) plus one semantic predicate.
3. Run B0, B1, B2 and the rank-ordering rule with the mock backend, and check result
   equality.
4. Repeat with the real backend on a 500-row subset, with caching on.
5. Write `results/E001/<sha>/{config.json,results.csv,environment.txt}`.

## Threats to validity

- The mock model's latency is simulated, so absolute latencies are not meaningful,
  only call counts and ratios.
- A real model's answers are noisy. Report its agreement with the labels separately
  from the ordering metrics.
- Selectivities in synthetic data are exact. Real optimizers must estimate them, so
  this experiment bounds the benefit from above.
