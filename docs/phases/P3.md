# P3 — SQL front end (M)

Text in, bound logical plan out. No execution. Three passes kept deliberately separate —
`Parser` (text → AST), `Binder` (AST → names and types resolved against the catalog),
`Planner` (bound statement → logical plan) — so that [P4](P4.md) can build and test plans
without going through SQL text at all.

**Scope is the full grammar P4 will execute**, not a single-table subset. A phase boundary
cutting through the parser means P4 reopens finished, tested code to add `JOIN`.

**Depends on:** [P2](P2.md) (the binder resolves against `Catalog`) · **Blocks:** [P4](P4.md) ·
**ROADMAP:** [§5 P3](../ROADMAP.md#p3--sql-front-end-m)

## Before you start — the minimum

1. **[*Crafting Interpreters*](https://craftinginterpreters.com/), ch 4 (Scanning),
   ch 5 (Representing Code), ch 6 (Parsing Expressions).** Free online. Nystrom's ch 6 is
   recursive descent done properly, including error recovery and synchronisation, which is
   the part most hand-written parsers get wrong. Roughly three hours and it is most of what
   3.1–3.3 need.
2. **[Pratt Parsers: Expression Parsing Made Easy](https://journal.stuffwithstuff.com/2011/03/19/pratt-parsers-expression-parsing-made-easy/)**
   — Nystrom again, ~20 minutes. This is the ~150 lines that replace Bison's per-precedence-
   level grammar rules. [*Crafting Interpreters* ch 17](https://craftinginterpreters.com/compiling-expressions.html)
   is the same technique in C, with a precedence table you can copy the shape of.
3. **15-445 Fall 2025, Lecture 2 — Modern SQL.** Not for parsing technique; for the
   *semantics* of the clauses you are about to bind. `GROUP BY`/`HAVING` scoping and
   aggregate placement rules are where binders get subtly wrong.

## Resources

### Specs & docs

- **[SQLite syntax diagrams](https://www.sqlite.org/lang.html)** — railroad diagrams per
  statement. The most usable grammar reference for the subset in scope; work directly from
  the `SELECT`, `INSERT`, `UPDATE`, `DELETE` and `CREATE TABLE` diagrams.
- **[PostgreSQL SQL commands](https://www.postgresql.org/docs/current/sql-commands.html)** —
  for tie-breaking semantics questions the SQLite diagrams do not answer.
- **[SQLite: The Lemon parser generator](https://sqlite.org/lemon.html)** — read the
  "Lemon vs. YACC" section even though you are hand-rolling. It is the clearest statement
  of what a generator buys and costs, and it corrects the roadmap (see below).
- **[DuckDB v2.0: Your Database Deserves a Better Parser](https://duckdb.org/2026/08/20/duckdb-20-peg-parser)**
  — why DuckDB abandoned its Bison/Postgres-derived grammar. The shift/reduce-conflict
  argument is the strongest available support for **not** using Bison here, and it is a
  better argument than the one the roadmap currently makes.
- **[Runtime-Extensible SQL Parsers Using PEG](https://duckdb.org/2024/11/22/runtime-extensible-parsers)**
  and the [CIDR 2025 paper](https://duckdb.org/pdf/CIDR2025-muehleisen-raasveldt-extensible-parsers.pdf)
  — optional depth on the same question.

### Books

- **[*Crafting Interpreters*](https://craftinginterpreters.com/), Nystrom.** ch 4–6 are the
  core. ch 17 (Compiling Expressions) for the Pratt table. Everything after ch 7 is
  interpreter/VM material this project does not need.
- **Sciore, *Database Design and Implementation* 2e, ch 9 (Parsing).** Short, and it is a
  *SQL* parser rather than a general-language one — lexer, then recursive descent, then the
  predicate/expression types a planner actually consumes.
- **[Eli Bendersky, Top-Down Operator Precedence Parsing](https://eli.thegreenplace.net/2010/01/02/top-down-operator-precedence-parsing)**
  — a second explanation of Pratt from a different angle. Worth reading if the first does
  not land; the technique is famously "obvious only after you've understood it".

### Video

- **15-445 Fall 2025, Lecture 1 — Relational Model & Algebra.** The algebra the logical
  plan represents. `Planner` output nodes are algebra operators; this is the vocabulary.
- **15-445 Fall 2025, Lecture 2 — Modern SQL.** Clause semantics, especially `GROUP BY`,
  `HAVING`, and where aggregates are and are not legal.

### Code to read

- **SQLite `parse.y`** — not to imitate, but to see the shape of a complete SQL grammar in
  one file. Useful as a checklist of syntax you have not thought about.
- **BusTub `src/binder/`** — a small binder over a catalog, in C++, with the same
  three-pass split. The closest structural match to what 3.6 builds.

### Skip

- **Flex and Bison.** Being deleted, not learned. [3.8](#38--remove-the-generator-toolchain)
  removes `src/parser/lexer.l`, `src/parser/parser.y` and the CI toolchain install.
- **The rest of *Crafting Interpreters*** — ch 7 onward is evaluation, closures, GC and a
  bytecode VM. P4 executes plans, not an AST tree-walker over a general-purpose language.
- **Query optimisation.** `Planner` produces a *logical* plan with no cost reasoning.
  [P8](P8.md) owns that, and it needs statistics and indexes that do not exist yet.
- **Window functions, CTEs, subqueries, `UNION`.** Not in the target grammar. Adding them
  later is additive precisely because the three passes are separate.

## Correction to file

> [ROADMAP:1047](../ROADMAP.md#p3--sql-front-end-m) says *"SQLite and DuckDB both
> hand-roll"* their parsers, in the **Precedent** row of the Bison-vs-recursive-descent
> table. Both halves are wrong:
>
> - **SQLite** uses [Lemon](https://sqlite.org/lemon.html), its own LALR(1) parser
>   *generator*. Lemon was written because YACC was unsuitable (non-reentrant, awkward
>   error handling) — an argument for a *better generator*, not for hand-rolling.
> - **DuckDB** used a Bison grammar forked from PostgreSQL (`third_party/libpg_query`)
>   through v1.x, and in [v2.0](https://duckdb.org/2026/08/20/duckdb-20-peg-parser)
>   replaced it with a **PEG** parser — again, generator to generator.
>
> **The decision still stands.** The other four rows of that table — expression precedence,
> error messages, no codegen step, debuggability — are unaffected, and DuckDB's stated
> reason for leaving Bison (LALR(1) grammars accrete shift/reduce conflicts as the grammar
> grows) *strengthens* the case against Bison here. Only the Precedent row needs replacing:
> the real hand-rolled precedents are **rustc**, **Go's `go/parser`**, **Roslyn** and
> **Clang**, all of which cite error-message quality as the reason.
>
> → offer for [§7 amendment log](../ROADMAP.md#7-amendment-log).

## Target grammar

Everything below must parse, bind and plan. From [§5 P3](../ROADMAP.md#p3--sql-front-end-m):

```sql
CREATE TABLE t (id INT32 PRIMARY KEY, name VARCHAR(64), emb VECTOR(768) NULL);
DROP TABLE t;
INSERT INTO t (id, name) VALUES (1, 'a'), (2, 'b');
UPDATE t SET name = 'c' WHERE id = 1;
DELETE FROM t WHERE id > 5;
SELECT a.id, COUNT(*) FROM a JOIN b ON a.id = b.a_id
  WHERE a.x > 5 AND b.y = 'z'
  GROUP BY a.id HAVING COUNT(*) > 2
  ORDER BY a.id DESC LIMIT 10;
```

## Implementation checklist

### 3.1 — Lexer

- [x] `Token` — kind, lexeme, line, column. **Position is not optional**; the gate asserts
      on it
      → `include/parser/token.h`
      → test: `LexerTest.TokenCarriesLineAndColumn`
- [x] Keyword table, case-insensitive; identifiers, including quoted
      → `src/parser/lexer.cpp`
      → test: `LexerTest.KeywordsAreCaseInsensitive`,
        `LexerTest.QuotedIdentifierPreservesCase`
- [x] Literals: integer, float, single-quoted string with `''` escaping, `NULL`, booleans
      → test: `LexerTest.EscapedQuoteInStringLiteral`,
        `LexerTest.IntegerVsFloatDisambiguation`
- [x] Operators and punctuation: `= <> != < <= > >= + - * / ( ) , . ;`
- [x] Comments (`--`, `/* */`) and whitespace, with line counting preserved across both
      → test: `LexerTest.LineCountSurvivesBlockComment`
- [x] Unterminated string and unterminated block comment produce a positioned error
      → test: `LexerTest.UnterminatedStringThrowsAtOpeningQuote`

### 3.2 — AST

- [x] Statement hierarchy: `SelectStatement`, `InsertStatement`, `UpdateStatement`,
      `DeleteStatement`, `CreateTableStatement`, `DropTableStatement`
      → `include/parser/ast.h`
- [x] Expression hierarchy: `ColumnRef`, `Literal`, `BinaryOp`, `UnaryOp`, `FunctionCall`
      (for `COUNT(*)` and friends), `Star`
- [x] Every node carries its source position, for the binder's error messages
      → test: `AstTest.EveryNodeCarriesPosition`
- [x] A structural printer, so parser tests assert on a stable string rather than on
      hand-built node trees
      → `src/parser/ast.cpp`
      → test: `AstTest.PrinterRoundTripsSimpleSelect`

### 3.3 — Recursive descent: statements

- [x] `Parser::Parse(std::string_view) -> std::unique_ptr<Statement>`
      → `include/parser/parser.h`, `src/parser/parser.cpp`
- [x] `CREATE TABLE` — column list, types (`INT32`, `INT64`, `FLOAT32`, `FLOAT64`,
      `BOOLEAN`, `VARCHAR(n)`, `VECTOR(n)`), `PRIMARY KEY`, `NULL`/`NOT NULL`
      → test: `ParserTest.CreateTableWithAllColumnTypes`,
        `ParserTest.VectorColumnCarriesDimension`
- [x] `DROP TABLE`
- [x] `INSERT` — optional column list, multiple `VALUES` tuples
      → test: `ParserTest.InsertMultipleValueTuples`,
        `ParserTest.InsertArityMismatchIsParsedNotRejected` — arity is the binder's job
- [x] `UPDATE` — `SET` assignment list, optional `WHERE`
- [x] `DELETE FROM` — optional `WHERE`
- [x] `SELECT` — projection list with `*` and qualified `a.id`, `FROM` with alias
      → test: `ParserTest.QualifiedColumnReference`, `ParserTest.TableAlias`
- [x] `JOIN ... ON`
      → test: `ParserTest.InnerJoinWithOnCondition`
- [x] `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY` with `ASC`/`DESC`, `LIMIT`
      → test: `ParserTest.FullSelectWithEveryClause` — the gate statement above, parsed
- [x] Clause-order enforcement: `GROUP BY` before `HAVING` before `ORDER BY` before `LIMIT`
      → test: `ParserTest.ClausesOutOfOrderIsASyntaxError`

### 3.4 — Pratt expressions

- [x] Precedence table: `OR` < `AND` < `NOT` < comparison < `+ -` < `* /` < unary < primary
      → `src/parser/expression_parser.cpp`
      → test: `ParserTest.AndBindsTighterThanOr`,
        `ParserTest.ComparisonBindsTighterThanAnd`,
        `ParserTest.MultiplicationBindsTighterThanAddition`
- [x] Left associativity for arithmetic and comparison
      → test: `ParserTest.SubtractionIsLeftAssociative` — `1 - 2 - 3` parses as `(1-2)-3`
- [x] Parenthesised subexpressions override precedence
      → test: `ParserTest.ParenthesesOverridePrecedence`
- [x] Unary minus and `NOT`
      → test: `ParserTest.UnaryMinusBindsTighterThanMultiplication`
- [x] Aggregate calls: `COUNT(*)`, `COUNT(x)`, `SUM`, `AVG`, `MIN`, `MAX`
      → test: `ParserTest.CountStarIsDistinctFromCountColumn`

### 3.5 — Error reporting

Error quality *is* the product for a REPL. This is the section that justifies the whole
hand-rolled decision, so it gets its own tests rather than riding along.

- [x] `SyntaxException` carrying line, column and the offending token
      → `include/utils/errors.h` — deriving from `AxolotException`
- [x] Messages name what was expected and what was found
      → test: `ParserTest.MissingFromReportsExpectedFrom`
- [x] **Position is asserted, not just the exception type.** "It threw" is not "it
      diagnosed"
      → test: `ParserTest.ErrorPositionPointsAtOffendingToken` — assert `line` and
        `column` numerically, for at least four distinct malformed statements
- [x] Statement-level synchronisation on error (skip to the next `;`), so a REPL can
      report more than one problem per input
      → test: `ParserTest.RecoversAtStatementBoundary`

### 3.6 — Binder

- [x] `Binder(const Catalog&)` and `Bind(const Statement&) -> unique_ptr<BoundStatement>`
      → `include/parser/binder.h`, `src/parser/binder.cpp`
- [x] Resolve table names and aliases to `TableId`
      → test: `BinderTest.UnknownTableThrowsNamingTheIdentifier` — assert the message
        contains the offending name **and** its position
- [x] Resolve column references, including qualified `a.id`, against the table's `Schema`
      → test: `BinderTest.UnknownColumnThrowsNamingTheIdentifier`,
        `BinderTest.AmbiguousColumnAcrossJoinedTablesThrows`,
        `BinderTest.QualifiedReferenceDisambiguates`
- [x] Expand `*` and `a.*` against the schema
      → test: `BinderTest.StarExpandsToSchemaOrder`
- [x] Type-check expressions and assignments
      → test: `BinderTest.TypeMismatchThrowsNamingBothTypes`,
        `BinderTest.InsertArityMismatchThrows`,
        `BinderTest.VectorDimensionMismatchThrows` — reuse
        `VectorDimensionMismatchException` from
        [`include/utils/errors.h`](../../include/utils/errors.h) rather than adding a new one
- [x] Aggregate legality: aggregates in `HAVING` and the projection list, not in `WHERE`;
      non-aggregated projections must appear in `GROUP BY`
      → test: `BinderTest.AggregateInWhereThrows`,
        `BinderTest.UngroupedColumnInProjectionThrows`
