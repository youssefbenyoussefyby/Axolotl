# P5 — WAL + recovery + latching (L)

Write-ahead logging, ARIES-style recovery, two-phase locking, and B8's page latch.

**Moved up from the original Phase 7**, and the reason is mechanical: P5 is the last point
where the set of things that write pages is small — `TableHeap`, `Catalog`, `VectorHeap`.
After B+Tree ([P6](P6.md)) and HNSW ([P7](P7.md)) exist, all of them need redo records, and
retrofitting recovery into a finished index is strictly more work than writing the index
against a logging API that already exists.
[N9](../ROADMAP.md#n9--vectorheap-data-pages-have-nowhere-to-put-a-page_lsn) is the proof:
vector data pages had nowhere to put a `page_lsn`, and that decision had to be made before a
graph inherited the layout.

**Depends on:** [P2](P2.md) (the `ILogManager` contract), [P4](P4.md) (the crash test needs a
SQL workload, and `TransactionManager`'s shape depends on how the executor threads a
transaction through operators) · **Blocks:** [P6](P6.md), [P7](P7.md), [P9](P9.md) ·
**ROADMAP:** [§5 P5](../ROADMAP.md#p5--wal--recovery--latching-l)

## Before you start — the minimum

1. **Mohan et al., [*ARIES*](https://cs.stanford.edu/people/chrismre/cs345/rl/aries.pdf)
   (TODS 1992), §1–3 and §6.** The paper is 68 pages; you need the model (§1–2), the data
   structures — transaction table, dirty page table, LSN, `prev_lsn` (§3), and the three
   recovery passes (§6). **Skip §4–5** (fine-granularity locking, nested top actions) and
   everything after §7. That is ~25 pages of the 68.
2. **15-445 Fall 2025, Lectures 21 and 22 — Database Logging, Database Recovery.** Pavlo
   walks ARIES's three passes with worked examples on a whiteboard. Watch these *before*
   the paper if the paper is heavy going; they cover the same ground in 150 minutes and the
   paper then reads as reference.
3. **15-445 Fall 2025, Lecture 18 — Two-Phase Locking.** Growing and shrinking phases,
   deadlock detection vs prevention, lock upgrades. 5.8's design is here.

## Resources

### Specs & docs

- **[PostgreSQL: Reliability and the Write-Ahead Log](https://www.postgresql.org/docs/current/wal.html)**
  — chapters 28–30. `wal.html`, `wal-intro.html`, `wal-internals.html`. Production framing of
  the same protocol, including why `fsync` placement is the whole game.
- **[SQLite: Write-Ahead Logging](https://www.sqlite.org/wal.html)** — a *different* design
  (the log holds the new pages, the database file holds the old), useful as a contrast that
  clarifies why ARIES does it the other way. Read after you understand ARIES, not before.
- **[SQLite: Atomic Commit](https://www.sqlite.org/atomiccommit.html)** — the clearest
  short explanation anywhere of what a crash can actually do to a file mid-write.
- **[BusTub Project #4 — Concurrency Control](https://15445.courses.cs.cmu.edu/fall2024/project4/)**
  — the lock manager assignment spec: lock modes, the compatibility matrix, upgrade rules.

### Books

- **Petrov, *Database Internals*, ch 5 — "Transaction Processing and Recovery".** Buffer
  management, steal/no-force, WAL, `LSN`, checkpoints, ARIES. The most approachable
  full-length treatment; read it before or instead of the paper's first half.
- **Sciore, *Database Design and Implementation* 2e, ch 5 — "Transaction Management".**
  Builds a recovery manager and a concurrency manager in code, bottom-up. The closest
  match to the *sequence* 5.1–5.8 follows.
- **Weikum & Vossen, *Transactional Information Systems*** — the reference work, if you
  want depth on 2PL correctness proofs. Not required; it is a textbook, not a guide.

### Video

- **15-445 Fall 2025, Lecture 17 — Concurrency Control Theory.** Serialisability,
  conflict graphs. The vocabulary 5.8's tests are written in.
- **15-445 Fall 2025, Lecture 18 — Two-Phase Locking.**
- **15-445 Fall 2025, Lecture 21 — Database Logging.**
- **15-445 Fall 2025, Lecture 22 — Database Recovery.** ARIES, all three passes.

### Code to read

- **BusTub `src/concurrency/lock_manager.cpp`** and `transaction_manager.cpp` — a lock
  manager at exactly this scale, in C++.
- **PostgreSQL `src/backend/access/transam/xlog.c`** — enormous, but `XLogInsert` and
  `XLogFlush` are worth reading for how the flush-up-to-LSN boundary is enforced.

### Skip

- **ARIES §4–5** — fine-granularity locking and nested top actions. The paper's title
  advertises them; this project does table- and row-granularity 2PL and does not need them.
- **MVCC.** Lecture 20, and Petrov's snapshot-isolation material. Explicit
  [§6.3 non-goal](../ROADMAP.md#63-non-goals). *"Attempting MVCC and crash recovery in one
  phase is where hobby databases stall"* — the tuple format's version byte
  ([P2 item 2.8](P2.md#28--tuple-format-version-byte)) is the entire budget spent on
  keeping the door open.
- **Timestamp-ordering and optimistic concurrency control.** Lecture 19. Same reason.
- **Distributed commit / 2PC.** Lectures 23–24. Out of scope.
- **Latch crabbing.** [P6](P6.md), and even there it is
  [deferred](../ROADMAP.md#64-accepted-debt-with-trigger-conditions) — the B+Tree takes a
  single tree latch until measured contention says otherwise.
- **Group commit.** [N6](../ROADMAP.md#n6--every-vectorheap-owns-a-private-filemanager-and-a-private-buffer-pool)
  notes P2 makes it *possible*; it is an optimisation, and P5 has enough correctness surface.

## Design decisions already made

| Decision | Where | Why |
|---|---|---|
| The WAL rule lives **inside `BufferPool`**, not at call sites | [§5 P5](../ROADMAP.md#p5--wal--recovery--latching-l) | A rule callers can forget is a rule that will be forgotten — the A4 lesson, when `Sync()` had zero call sites |
| Steal / no-force, therefore both redo **and** undo | [§5 P5](../ROADMAP.md#p5--wal--recovery--latching-l) | The pool already steals: it evicts dirty pages |
| ARIES-lite: analysis → redo → undo | [§5 P5](../ROADMAP.md#p5--wal--recovery--latching-l) | Follows from steal/no-force |
| Two-phase locking, table- then row-granularity | [§5 P5](../ROADMAP.md#p5--wal--recovery--latching-l), [§6.3](../ROADMAP.md#63-non-goals) | MVCC is a non-goal |
| B8's page latch lands here, **not optional** | [§5 P5](../ROADMAP.md#p5--wal--recovery--latching-l), amendment #3 | P9 puts concurrent clients on a pool whose own header documents pages as unsafe to share |
| `ILogManager`/`NullLogManager` already exist from P2 | [P2 item 2.7](P2.md#27--the-wal-contract-not-the-implementation) | **No call site changes in this phase** |

## Implementation checklist

### 5.1 — Log record format and append

- [ ] `LogRecordType` and `LogRecordHeader` per
      [§5 P5](../ROADMAP.md#p5--wal--recovery--latching-l): `lsn`, `prev_lsn`, `txn_id`,
      `type`, `_pad[3]`, `size`
      → `include/storage/wal.h`
      → test: `WalTest.HeaderLayoutIsStable` — raw-byte assertion, per P1's lesson 3
- [ ] Per-type payloads: `kInsert`/`kDelete` carry the RID and the tuple bytes;
      `kUpdate` carries **both** before- and after-images (undo needs the before-image);
      `kNewPage` carries the `PageRef`
      → test: `WalTest.UpdateRecordCarriesBeforeAndAfterImages`
- [ ] `LogManager(StorageManager&, const std::string& log_path)` and
      `Append(header, payload) -> lsn`
      → `src/storage/wal.cpp`
      → test: `WalTest.AppendReturnsMonotonicLsns`,
        `WalTest.AppendedRecordsReadBackInOrder`
- [ ] **Validate records read back off disk** — a truncated tail is the *expected* state
      after a crash, not a corruption
      → test: `WalTest.TruncatedTailRecordIsIgnoredNotMisparsed`,
        `WalTest.GarbageAfterValidTailStopsReplay`
      → this is [P1's lesson 1](P1.md#1-trust-nothing-that-came-off-disk) applied to
        the log; without it, recovery is the code most likely to read past its buffer

### 5.2 — The WAL protocol inside the buffer pool

      → test: `WalTest.FlushUpToMakesRecordsDurable`,

- [ ] `BufferPool` calls `log_manager_.FlushUpTo(page.PageLsn())` before **every** page

      → [`src/storage/buffer_pool.cpp`](../../src/storage/buffer_pool.cpp)

      call site changed** — that was the whole point of the P2 contract
      → verify: `git diff --stat` for this item touches the wiring, not the callers

- [ ] Replay forward from the earliest dirty-page `recLSN`

## Gate — a real crash test

From [§5 P5](../ROADMAP.md#p5--wal--recovery--latching-l):

- [ ] A **child process** opens the database, commits some transactions, leaves others
      open, and is **killed with no cleanup** (`SIGKILL` / `TerminateProcess` — not a
      graceful exit, which would defeat the test)
- [ ] The parent reopens, runs recovery, and asserts committed rows **present** and
      uncommitted rows **absent**
      → `tests/integration/recovery_test.cpp`
      → test: `RecoveryGate.CommittedSurvivesKillUncommittedDoesNot`

This is genuinely testable, unlike the fsync-reaches-the-platter gap `audit.md` correctly
calls untestable. Killing a process proves the *recovery algorithm* is correct, which is the
claim being made; A4's untestable claim was about hardware.

Note the platform split: the test needs `fork`/`kill` on POSIX and
`CreateProcess`/`TerminateProcess` on Windows, and both `build-windows` and the Linux
surfaces must run it. Budget for that — it is real work, not boilerplate.
