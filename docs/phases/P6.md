# P6 — Relational indexing (L)

A disk-backed B+Tree, one node per page through the `StorageManager`, plus a hash index for
equality-only lookups and the `IndexScan` operator that makes them reachable from SQL.

**WAL-aware and latch-aware from the first line**, because [P5](P5.md) already exists. That
is the entire point of the reordering: retrofitting recovery into a finished index is
strictly more work than writing the index against a logging API that is already there.

**Why indexing sits after execution, when CMU's order is the reverse.** The counter-argument
is real — `IndexScan` and index selection both depend on the B+Tree. It loses because a
B+Tree with no query path is testable only by unit test, whereas a seq-scan executor is a
*demonstrable database*; and because `IndexScan` is one more operator inside an established
framework, given [P4](P4.md) defined the operator interface properly.

## Before you start — the minimum

1. **15-445 Fall 2025, Lectures 8 and 9 — Indexes & Filters I & II.** B+Tree structure,
   the difference between a B-Tree and a B+Tree (leaves hold all the data, and they are
   linked — which is what makes range scans cheap), split and merge, and design decisions
   like node size and variable-length keys.
2. **Petrov, *Database Internals*, ch 2 ("Introduction to B-Trees") and ch 4
   ("Implementing B-Trees").** Ch 4 is the one that matters: page headers for nodes,
   rightmost pointers, sibling links, split/merge mechanics, and the "propagate the split
   upward" recursion that is where most first implementations break.
3. **15-445 Fall 2025, Lecture 10 — Index Concurrency Control.** Latch crabbing is
   [deferred](../ROADMAP.md#64-accepted-debt-with-trigger-conditions), so watch this to
   understand what you are *choosing not to do* and what the single-tree-latch contract
   costs. Deferring knowingly is different from not knowing.

### Skip

- **Latch crabbing / hand-over-hand traversal.** Explicitly
  [deferred](../ROADMAP.md#64-accepted-debt-with-trigger-conditions) with the trigger
  *"first measured contention on the tree latch"*. 6.7 takes one tree latch and **writes the
  contract down** rather than implying it.
- **B-link trees / Lehman-Yao.** The right answer once crabbing is on the table. Not now.
- **LSM-trees.** A different storage architecture, not an index you add to this one.
- **Bloom filters.** Lecture 9's second half. Useful with LSM-trees; nothing here consumes
  one.
- **Index selection and cost.** [P8](P8.md). P6 makes `IndexScan` *available*; P8 decides
  when to *choose* it.
- **Covering indexes / index-only scans.** Additive later, and they need P8's statistics to
  be worth anything.

## The one that gets missed

[§5 P6](../ROADMAP.md#p6--relational-indexing-l) flags it explicitly: **`TableHeap::Update`
can change a row's RID** ([P2 item 2.5](P2.md#25--tableheap)), and every index entry
pointing at the old RID is then stale. It is the case most likely to be missed because it
only fires when an update *grows* a row past its slot, which a small test fixture never does.

It gets its own item (6.10) and its own test, and the test must use rows large enough to
force the relocation.

## Implementation checklist

### 6.1 — The Index interface

- [ ] `Index` — `Insert(const Value&, RID)`, `Delete(const Value&, RID)`,
      `Lookup(const Value&) -> std::vector<RID>`
      → `include/index/index.h`
      → test: `IndexTest.LookupReturnsEveryRidForADuplicateKey`
- [ ] `IndexMetadata` — name, table, key column(s), uniqueness, index type
      → `include/index/index.h`
      → test: `IndexTest.UniqueIndexRejectsDuplicateKey`

### 6.2 — Node layout

- [ ] `BPlusTreeNode` header on top of the standard 24-byte `PageHeader`: node type,
      key count, parent `PageRef`, and for leaves the next-sibling `PageRef`
      → `include/index/btree/btree_node.h`
      → test: `BTreeNodeTest.HeaderLayoutIsStable` — raw bytes
- [ ] Internal node: n keys, n+1 child `PageRef`s
- [ ] Leaf node: n keys, n RIDs, sibling link
      → test: `BTreeNodeTest.LeafSiblingLinkSurvivesReopen`
- [ ] **`ValidateOrThrow` for nodes.** [P1's lesson 1](P1.md#1-trust-nothing-that-came-off-disk):
      key counts and child pointers off disk are untrusted input, exactly as
      [N1](../ROADMAP.md#n1--page-never-validates-a-header-or-slot-entry-that-came-off-disk)
      was for `Page`
      → test: `BTreeNodeTest.KeyCountBeyondCapacityThrows`,
        `BTreeNodeTest.ChildPointerOutsideFileThrows`
- [ ] Max fan-out computed from key size and `PAGE_SIZE - sizeof(PageHeader) - sizeof(NodeHeader)`
      → test: `BTreeNodeTest.FanOutMatchesComputedCapacity`

### 6.3 — Search and insert

- [ ] `BPlusTreeIndex(StorageManager&, FileId, ColumnType)`, root tracked in a header page
      → `src/index/btree/btree_index.cpp`
      → test: `BTreeTest.EmptyTreeLookupReturnsNothing`,
        `BTreeTest.RootPageRefSurvivesReopen`
- [ ] Descend to leaf; binary search within a node
      → test: `BTreeTest.InsertThenLookupRoundTrips`
- [ ] Leaf split, with the median promoted to the parent
      → test: `BTreeTest.LeafSplitPreservesAllKeys`,
        `BTreeTest.SplitAtExactCapacityBoundary`
- [ ] Internal split, propagating recursively; new root when the old root splits
      → test: `BTreeTest.RootSplitIncreasesHeight`,
        `BTreeTest.ThousandSequentialInsertsAllFindable` — sequential insert is the
        worst case for split behaviour and the fastest way to find an off-by-one
      → test: `BTreeTest.ThousandRandomInsertsAllFindable`

### 6.4 — Delete and merge

- [ ] Leaf delete
      → test: `BTreeTest.DeletedKeyIsNotFound`,
        `BTreeTest.DeleteOfAbsentKeyIsANoOp`
- [ ] Redistribute from a sibling when under-full
      → test: `BTreeTest.RedistributionPreservesOrdering`
- [ ] Merge with a sibling, removing the separator from the parent
      → test: `BTreeTest.MergePropagatesToParent`,
        `BTreeTest.RootCollapsesWhenItHasOneChild` — height *decreasing* is the case
        symmetric to the root split, and the one most often left unimplemented
- [ ] Delete everything, then reinsert
      → test: `BTreeTest.EmptyAfterDeletingAllKeysThenUsableAgain`

### 6.5 — Range scan and iterator

- [ ] `Range(const Value& lo, const Value& hi) -> std::vector<RID>`
      → test: `BTreeTest.RangeReturnsKeysInOrder`,
        `BTreeTest.RangeBoundsAreInclusiveAsDocumented`,
        `BTreeTest.EmptyRangeReturnsNothing`
- [ ] `Iterator` — ordered forward traversal via leaf sibling links
      → `src/index/btree/btree_iterator.cpp`
      → test: `BTreeIteratorTest.VisitsEveryKeyInSortedOrder`,
        `BTreeIteratorTest.SurvivesEvictionMidTraversal` — the iterator holds guards;
        [N5](../ROADMAP.md#n5--gettuple-hands-out-a-span-into-a-frame-that-can-be-evicted-underneath-it)
        again, in a new place

### 6.6 — WAL integration

Free, because [P5](P5.md) exists. That is the payoff for the reordering.

- [ ] Log every structural modification: insert, delete, split, merge, root change
      → `src/index/btree/btree_index.cpp`
      → test: `BTreeRecoveryTest.SplitSurvivesCrash`,
        `BTreeRecoveryTest.MergeSurvivesCrash`
- [ ] A crash **mid-split** — the case where the tree is momentarily inconsistent — recovers
      to a valid tree
      → test: `BTreeRecoveryTest.CrashBetweenSplitAndParentUpdateRecovers`
- [ ] A whole-tree structural validator, used as a test oracle throughout this phase
      → `src/index/btree/btree_index.cpp` (debug-only)
      → test: `BTreeTest.StructuralInvariantsHoldAfterRandomWorkload` — every node
        within fan-out bounds, keys sorted, leaf depths equal, sibling chain complete

### 6.7 — Latching

- [ ] One reader/writer latch for the whole tree, taken through [P5](P5.md)'s mechanism
      → test: `BTreeTest.ConcurrentReadersCoexist`,
        `BTreeTest.WriterExcludesReaders`
- [ ] **Write the contract down** — the deferral is a decision, not an omission. State that
      traversal takes the tree latch rather than hand-over-hand, and name the trigger for
      revisiting it ([§6.4](../ROADMAP.md#64-accepted-debt-with-trigger-conditions):
      first measured contention)
      → `include/index/btree/btree_index.h`

### 6.8 — Hash index

- [ ] `HashIndex` — equality-only, `Lookup` and nothing ordered
      → `src/index/hash/hash_index.cpp`
      → test: `HashIndexTest.LookupRoundTrips`,
        `HashIndexTest.CollisionChainReturnsAllRids`,
        `HashIndexTest.SurvivesReopen`
- [ ] `Range` is unsupported and says so, rather than returning something plausible
      → test: `HashIndexTest.RangeThrowsUnsupported`

### 6.9 — IndexScan operator

- [ ] `IndexScanExecutor`, inside [P4](P4.md)'s existing framework
      → `src/executor/operators/index_scan.cpp`
      → test: `IndexScanTest.EqualityLookupReturnsSameRowsAsSeqScanWithFilter` —
        cross-validation against the already-trusted path, the technique used
        throughout [P4](P4.md)
      → test: `IndexScanTest.RangeScanReturnsRowsInKeyOrder`
- [ ] `PhysicalIndexScan` in the plan hierarchy, selectable by rule
      → `include/optimizer/physical_plan.h`
      → test: `PhysicalPlanTest.EqualityPredicateOnIndexedColumnSelectsIndexScan`

### 6.10 — Index maintenance on every DML path

- [ ] `Insert` maintains every index on the table
      → `src/executor/operators/insert.cpp`
      → test: `IndexMaintenanceTest.InsertIsVisibleThroughEveryIndex`
- [ ] `Delete` removes every index entry
      → test: `IndexMaintenanceTest.DeleteRemovesEntryFromEveryIndex`
- [ ] **`Update` handles the RID change.** Rows must be large enough to force relocation
      → `src/executor/operators/update.cpp`
      → test: `IndexMaintenanceTest.GrowingUpdateRepointsIndexToNewRid` — the one from
        [the section above](#the-one-that-gets-missed)
      → test: `IndexMaintenanceTest.IndexNeverPointsAtATombstone` — run a mixed
        insert/update/delete workload, then assert every index entry resolves to a live row
- [ ] Index changes participate in transaction rollback
      → test: `IndexMaintenanceTest.AbortedInsertLeavesNoIndexEntry`

### 6.11 — DDL

- [ ] `CREATE INDEX` / `DROP INDEX` in the parser, binder and planner
      → `src/parser/parser.cpp`, `src/parser/binder.cpp`
      → test: `ParserTest.CreateIndexStatement`
- [ ] Index metadata persisted in the `Catalog`, and indexes reopened with the table
      → `src/catalog/catalog.cpp`
      → test: `CatalogTest.IndexMetadataSurvivesReopen`
- [ ] Building an index over an **already-populated** table
      → test: `CreateIndexTest.BuiltOverExistingRowsFindsAllOfThem`

## Gate

[§5 P6](../ROADMAP.md#p6--relational-indexing-l) does not state a single-sentence gate the
way other phases do. Deriving one in the same spirit — end-to-end, against real files, with
an independent oracle:

- [ ] Build a table of 100 000 rows with an index, close everything, reopen
- [ ] Point lookups, range scans and an ordered full traversal all agree with the
      equivalent `SeqScan` + `Filter` + `Sort` result
- [ ] A mixed insert/update/delete workload — with updates that **grow** rows — leaves
      every index entry resolving to a live row
- [ ] Structural invariants hold after that workload
- [ ] The whole thing survives a kill-and-recover, per [P5](P5.md)'s gate technique
      → `tests/integration/index_test.cpp`
      → test: `IndexingGate.IndexAgreesWithSeqScanAcrossReopenAndCrash`
