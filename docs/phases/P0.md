# P0 — Hardening (S)

Close the four blocking findings from the Phase 1 audit and establish a green CI baseline
for the first time. Every phase gate in the roadmap is phrased as *"these tests pass"*;
until the project compiles on the platforms those tests run on, no gate means anything.

**Depends on:** nothing · **Blocks:** everything ·
**ROADMAP:** [§5 P0](../ROADMAP.md#p0--hardening-s) · [§2 findings N1–N14](../ROADMAP.md#2-phase-1-audit--findings-n1n14)

---

## Before you start — the minimum

1. **[ROADMAP §2, N1 through N4](../ROADMAP.md#blocking--nothing-else-is-verifiable-until-these-are-done).**
   Re-read the four blocking findings with the source open beside them. Each one names a
   file and a line; confirm the line still says what the finding says it does before you
   change it. Two of them (N1, N10) compound each other and the fix order depends on that.
2. **[GCC C++ Standards Support](https://gcc.gnu.org/projects/cxx-status.html)** — five
   minutes, and only the `<format>` row. `std::format` landed in libstdc++ with **GCC 13.1**
   (April 2023); the CI matrix runs gcc-11 and libstdc++-12. That is N2 in one sentence, and
   it is why six of seven CI surfaces cannot compile today.
3. **[AddressSanitizer](https://github.com/google/sanitizers/wiki/AddressSanitizer)** — the
   "Heap buffer overflow" section. The `PageCorruption` suite you are about to write is
   supposed to trip ASan *before* the fix and throw cleanly *after*. Knowing how to read
   the report is the difference between "the test fails" and "the test proved N1 is real".

Everything below is lookup.

### Code to read

- **[SQLite database file format §1.6](https://www.sqlite.org/fileformat2.html)** —
  the b-tree page header, and how SQLite words each field's valid range. It is the clearest
  published statement of the invariants N1 is missing. Note that SQLite documents *cell
  content area* and *first freeblock* with explicit bounds for the same reason.
- **`src/storage/page.cpp`**, all of it. It is short, and P0 is the last time you will read
  it without a `PageGuard` in the way.

### Skip

- **`PageGuard` / RAII pins.** Tempting here — N4 is a leak, and RAII is the answer. It is
  [P2](P2.md) work: [amendment #1](../ROADMAP.md#7-amendment-log) settled that P2 rewrites
  every storage call site anyway, so introducing the guard now means touching them twice.
  P0 uses a local scope guard in exactly two functions and stops.
- **CRC32 / page checksums.** Also P2 ([§4.1](../ROADMAP.md#41-page--4096-bytes-fixed-at-compile-time)),
  and it needs the 24-byte header. `ValidateOrThrow` catches structural corruption without
  it; a checksum catches the rest. Doing them together is one format change instead of two.
- **Fixing B7 (page compaction).** Open in the audit, correctly deferred to
  [P2's `TableHeap`](../ROADMAP.md#tableheap), which is what makes reclaimed space reusable.
  `DeletedSpaceIsNotReclaimed_B7` pins today's behaviour deliberately — do not "fix" it here.

## Design decisions already made

Do not re-open these mid-phase:

| Decision | Where |
|---|---|
| `CorruptPageException`, not `InvalidPageException` — "the disk is bad" ≠ "your argument is bad" | [N1](../ROADMAP.md#n1--page-never-validates-a-header-or-slot-entry-that-came-off-disk) |
| The four invariants are checked **in order**; each depends on the previous holding | [N1's table](../ROADMAP.md#n1--page-never-validates-a-header-or-slot-entry-that-came-off-disk) |
| `UnpinPage` applies `is_dirty` *before* the pin check, and throws rather than returning | [N3](../ROADMAP.md#n3--unpinpage-silently-discards-the-dirty-flag-on-an-unbalanced-unpin) |
| Scope guard in two places now; `PageGuard` in P2 | [N4](../ROADMAP.md#n4--pin-leaks-on-the-exception-paths-and-no-raii-to-prevent-them), amendment #1 |
| `docs/` ships, scratch notes outside it stay local | [N11](../ROADMAP.md#n11--the-design-documents-are-gitignored) |

- [x] Invariant 1 — `slot_count <= (PAGE_SIZE - sizeof(PageHeader)) / sizeof(SlotEntry)`.

- [x] Invariant 3 — `free_ptr <= PAGE_SIZE`
- [x] Invariant 4 — for each live slot, `offset >= free_ptr && offset + length <= PAGE_SIZE`.

### 0.5 — N4: close the two live pin leaks

Scope guard only. Not `PageGuard`.

- [x] ~~Test that a throw mid-loop leaves zero pins held~~ **Not written, and it would
      be a dishonest test.** With the temporary gone there is no longer any statement
      between fetch and unpin that *can* throw, so there is nothing to inject a failure
      into without adding a seam that exists only for the test. The property is now
      structural, not behavioural. `PageGuard` in [P2](P2.md) is what makes it
      enforceable rather than merely true, and that is where the test belongs
- [x] ~~Scope-guard the `Put` loop~~ **No leak to fix.** Each iteration acquires and
      releases within itself, and `Put` holds a pin only across `memcpy` and
      `MarkDirty`, neither of which can throw. The finding overstated this — see
      [ROADMAP N4](../ROADMAP.md#n4--pin-leaks-on-the-exception-paths-and-no-raii-to-prevent-them)
- [x] `Get` leaked exactly **one** pin, via a `std::vector<float>` temporary built
      *between* `FetchPage` and `UnpinPage`. Fixed by deleting the temporary rather
      than guarding it: it copied page bytes into a vector and then element-by-element
      into `result`, so copying straight into `result` removes the throw point *and* a
      redundant copy of every page on the read path. Nothing between fetch and unpin
      can throw now, in either loop
- [x] Leave a `// P2: replace with PageGuard` marker at both sites so P2's sweep finds them
      → `src/storage/vector_heap.cpp`
