# P8 — Optimizer + statistics (M)

Cost-based planning: statistics, cardinality estimation, a cost model, index selection and
join ordering.

**Split out of the old Phase 3** because *a cost model with no statistics and no indexes to
choose between is a random number generator.* By P8 both exist — [P6](P6.md) gave you
indexes to choose between, [P4](P4.md) gave you two join implementations to choose between,
and the logical/physical split means choosing is an *addition* rather than a rewrite.

**Depends on:** [P4](P4.md), [P6](P6.md) · **Blocks:** nothing ·
**ROADMAP:** [§5 P8](../ROADMAP.md#p8--optimizer--statistics-m)

## Before you start — the minimum

1. **15-445 Fall 2025, Lectures 15 and 16 — Query Planning & Optimization I & II.**
   Lecture 15 covers rule- vs cost-based optimisation and the search space; Lecture 16
   covers cardinality estimation, histograms, sampling, and the dynamic-programming join
   enumeration 8.6 implements. These two lectures are almost the whole phase.
2. **Selinger et al., *Access Path Selection in a Relational Database Management System*
   (SIGMOD 1979).** ~12 pages, and it is the origin of everything in this phase: the cost
   formulas, selectivity estimation, and the bottom-up DP over join orders — which is still
   called "Selinger-style" optimisation. Available via the
   [Red Book](http://www.redbook.io/all-chapters.html), which also carries Hellerstein's
   editorial introduction to why it mattered.
3. **[*How Query Engines Work*](https://howqueryengineswork.com/), the query-planner
   chapters.** The same book used in [P4](P4.md); its treatment of physical planning and
   cost is directly applicable.

### Video

- **15-445 Fall 2025, Lecture 15 — Query Planning & Optimization I.**
- **15-445 Fall 2025, Lecture 16 — Query Planning & Optimization II.** Cardinality
  estimation and join ordering.

### Code to read

- **PostgreSQL `src/backend/optimizer/README`** — a genuinely good architectural document
  for the planner, path/plan distinction included.
- **BusTub `src/optimizer/`** — rule-based, small, and it shows where a cost-based pass
  would slot into the same structure.

### Skip

- **Cascades / Volcano-style transformational optimisers.** The right architecture for an
  extensible optimiser and far more machinery than this needs. The Selinger bottom-up DP
  in 8.6 is the correct scope.
- **Genetic / randomised join enumeration.** Postgres's GEQO. The greedy fallback past 8
  relations is enough.
- **Multi-column and dependency statistics.** Postgres's `CREATE STATISTICS`. Single-column
  histograms first; correlated predicates are a known, documentable inaccuracy.
- **Adaptive / runtime re-optimisation.** A research topic.
- **Sampling-based estimation.** 8.2 does a full scan for `ANALYZE`. At this scale that is
  fine and it removes a large source of test nondeterminism.

## Why the gate is a plan assertion, not a timer

[§5 P8](../ROADMAP.md#p8--optimizer--statistics-m) requires *"a query whose physical plan
demonstrably changes when an index is added — asserted on the plan tree, not on timing."*

Timing assertions in CI are flaky by construction: shared runners, cold caches, and
sanitizer builds that are 10× slower. A plan assertion is deterministic, and it tests the
claim actually being made — *the optimiser chose differently* — rather than a proxy for it.
This is expressible only because [P4](P4.md) defined the logical/physical split properly;
it is that decision's payoff.

Keep the benchmark separately, under `benchmarks/`, as evidence rather than as a gate.

## Implementation checklist

### 8.1 — Statistics types

- [ ] `ColumnStats` — `distinct_count`, `null_count`, `min`, `max`, `histogram`
      → `include/catalog/statistics.h`
      → test: `StatisticsTest.EmptyColumnStatsAreWellFormed`
- [ ] `TableStats` — row count, page count, per-column stats
      → test: `StatisticsTest.TableStatsAggregatesColumnStats`
- [ ] Equi-depth histogram construction from a sorted sample
      → `src/catalog/statistics.cpp`
      → test: `HistogramTest.EquiDepthBucketsHoldEqualCounts`,
        `HistogramTest.SkewedDistributionStillProducesEqualDepthBuckets` — the whole
        reason equi-depth beats equi-width
      → test: `HistogramTest.FewerDistinctValuesThanBucketsIsHandled`
- [ ] Histogram selectivity query: fraction of rows satisfying `< v`, `<= v`, `= v`,
      `BETWEEN`
      → test: `HistogramTest.SelectivityOfFullRangeIsOne`,
        `HistogramTest.SelectivityOutsideMinMaxIsZero`,
        `HistogramTest.SelectivityIsMonotonicInThreshold`

### 8.2 — Collection and persistence

- [ ] `ANALYZE` — full scan computing stats per column
      → `src/catalog/statistics.cpp`
      → test: `AnalyzeTest.RowCountMatchesActual`,
        `AnalyzeTest.NullCountMatchesActual`,
        `AnalyzeTest.MinMaxMatchActual`
- [ ] `ANALYZE` statement in parser, binder, planner
      → test: `ParserTest.AnalyzeStatement`
- [ ] Stats persisted in the `Catalog` and reloaded on open
      → `src/catalog/catalog.cpp`
      → test: `CatalogTest.StatisticsSurviveReopen`
- [ ] Absent stats produce documented defaults, not a crash or a zero — an un-analysed
      table must still plan
      → test: `CostModelTest.MissingStatisticsUsesDocumentedDefaults`

### 8.3 — Cardinality estimation

- [ ] Selectivity of a single predicate, from the histogram
      → `src/optimizer/cost_model.cpp`
      → test: `CardinalityTest.EqualityOnUniqueColumnEstimatesOne`,
        `CardinalityTest.RangePredicateUsesHistogram`
- [ ] Conjunction and disjunction. **Independence is assumed**; document that, because it
      is the single largest source of estimation error and a future reader deserves to
      know it was a choice
      → test: `CardinalityTest.ConjunctionMultipliesSelectivities`,
        `CardinalityTest.DisjunctionUsesInclusionExclusion`
- [ ] Join cardinality from the classic `|R| × |S| / max(distinct_R, distinct_S)`
      → test: `CardinalityTest.EquiJoinCardinalityMatchesFormula`,
        `CardinalityTest.JoinWithEmptyRelationIsZero`
- [ ] Estimates are never zero — a zero estimate makes every downstream cost zero and
      collapses the search
      → test: `CardinalityTest.EstimateIsAtLeastOne`

### 8.4 — Cost model

- [ ] `Cost { double io; double cpu; Total(); }` and `CostModel::Estimate`
      → `include/optimizer/cost_model.h`, `src/optimizer/cost_model.cpp`
- [ ] Per-operator costs: SeqScan, IndexScan, NestedLoopJoin, HashJoin, Sort, Aggregate
      → test: `CostModelTest.SeqScanCostScalesWithPageCount`,
        `CostModelTest.IndexScanCheaperThanSeqScanAtLowSelectivity`,
        `CostModelTest.SeqScanCheaperThanIndexScanAtHighSelectivity` — the crossover
        is the entire point of having a cost model, and both directions must be pinned
      → test: `CostModelTest.HashJoinCheaperThanNestedLoopAtScale`
- [ ] IO/CPU weighting constants named and documented in one place, not scattered
      → `include/optimizer/cost_model.h`
- [ ] Cost is monotonic in input size
      → test: `CostModelTest.CostIncreasesWithInputCardinality`

### 8.5 — Index selection

- [ ] Replace [P4](P4.md)'s fixed rule with a cost comparison — **in the one function
      [P4 item 4.4](P4.md#44--joins-with-the-physical-split-intact) isolated for exactly
      this purpose**
      → `src/optimizer/rule_optimizer.cpp`
      → verify: the diff touches that function and the cost model, not the executors
- [ ] Match predicates to available indexes, including which index when several apply
      → test: `IndexSelectionTest.EqualityPredicateSelectsMatchingIndex`,
        `IndexSelectionTest.MostSelectiveIndexWinsWhenSeveralApply`,
        `IndexSelectionTest.NoUsableIndexFallsBackToSeqScan`
- [ ] An `ORDER BY` matching an index's key order can skip the sort
      → test: `IndexSelectionTest.OrderByMatchingIndexEliminatesSortNode`

### 8.6 — Join ordering

- [ ] Bottom-up DP over subsets, for ≤ 8 relations
      → `src/optimizer/join_optimizer.cpp`
      → test: `JoinOrderTest.TwoRelationsPickCheaperOrder`,
        `JoinOrderTest.SmallRelationBecomesHashBuildSide`,
        `JoinOrderTest.FourRelationChainFindsOptimalOrder` — assert against an order
        computed by brute-force enumeration in the test, not a hardcoded expectation
- [ ] Greedy fallback beyond 8, and the threshold named as a constant with the reasoning
      → test: `JoinOrderTest.NineRelationsUsesGreedyAndTerminates`,
        `JoinOrderTest.GreedyResultIsWithinBoundOfDpOnEightRelations`
- [ ] Cross products avoided unless unavoidable
      → test: `JoinOrderTest.CrossProductAvoidedWhenAJoinPredicateExists`
- [ ] `EXPLAIN`, printing the physical plan with estimated cardinality and cost
      → `src/optimizer/physical_plan.cpp`, `src/parser/parser.cpp`
      → test: `ExplainTest.PrintsPlanTreeWithCosts` — this is also the debugging tool
        that makes the rest of the phase tractable; build it early if 8.4 gets murky

## Gate

From [§5 P8](../ROADMAP.md#p8--optimizer--statistics-m):

- [ ] A query whose **physical plan demonstrably changes when an index is added** —
      asserted on the **plan tree**, not on timing
      → `tests/integration/optimizer_test.cpp`
      → test: `OptimizerGate.AddingAnIndexChangesTheChosenPhysicalPlan` —
        run `EXPLAIN` before and after `CREATE INDEX` on a populated, analysed table;
        assert `PhysicalSeqScan` becomes `PhysicalIndexScan`
- [ ] The two plans return **identical rows** — a faster wrong plan is not an optimisation
      → test: `OptimizerGate.OptimisedPlanReturnsIdenticalRows`
