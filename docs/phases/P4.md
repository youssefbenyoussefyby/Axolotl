# P4 — Execution engine (XL)

Volcano iterator model: every operator is a `Next()` that pulls from its children. This is
the phase that turns storage plus a parser into a database you can actually query.

It is also, per [ROADMAP](../ROADMAP.md#p4--execution-engine-xl), **one of two phases where
the project is most likely to stall.** The mitigation is structural and it is item
[4.2](#42--the-milestone-seqscan--filter--projection) below: get SeqScan + Filter +
Projection running end-to-end against real files *before* touching joins. That is a working
database. Everything after it is addition rather than integration, and the difference
matters when momentum runs out.

**Depends on:** [P2](P2.md), [P3](P3.md) · **Blocks:** [P5](P5.md) (the crash test needs a
workload), [P6](P6.md), [P8](P8.md) ·
**ROADMAP:** [§5 P4](../ROADMAP.md#p4--execution-engine-xl)

## Before you start — the minimum

1. **Graefe, [*Volcano — An Extensible and Parallel Query Evaluation System*](https://cs-people.bu.edu/mathan/reading-groups/papers-classics/volcano.pdf)
   (TKDE 1994), §2–3.** The iterator model in the words of the person who named it. Skip
   the `exchange` operator and everything about parallelism — that is the half of the paper
   this project does not use. ~15 pages of the relevant part.
2. **15-445 Fall 2025, Lectures 13–14 — Query Execution I & II.** Lecture 13 is processing
   models (iterator vs materialisation vs vectorised) and access methods; it is the direct
   justification for the choice already made. Lecture 14 covers parallelism — watch for
   context, implement none of it.
3. **15-445 Fall 2025, Lecture 12 — Join Algorithms.** Nested loop (naive, block, index) and
   hash join, including the build/probe split and partitioning. 4.4 implements two of these.

### Skip

- **Vectorised / push-based execution.** Explicitly not chosen
  ([§5 P4](../ROADMAP.md#p4--execution-engine-xl)): vectorisation is retrofitted for speed
  once correctness exists, and the iterator model is what every reference here uses, which
  matters when debugging at 1am.
- **Parallel query execution.** Volcano's `exchange` operator, Lecture 14's second half.
  P9 delivers concurrent *clients*; intra-query parallelism is not in scope anywhere.
- **Cost-based operator selection.** [P8](P8.md). P4 picks with a fixed rule.
- **Index-based joins and IndexScan.** [P6](P6.md), because there is no index yet. 4.4's
  `PhysicalJoin` interface is what makes adding them additive.
- **Sort-merge join.** Not in [§5 P4's](../ROADMAP.md#p4--execution-engine-xl) operator
  list. It becomes attractive once P6 gives you ordered B+Tree scans; revisit then.

## Design decisions already made

| Decision | Where | Consequence if re-opened |
|---|---|---|
| Volcano iterator, not vectorised or push | [§5 P4](../ROADMAP.md#p4--execution-engine-xl) | Every operator's shape changes |
| `LogicalJoin` → `PhysicalJoin` interface with **both** NLJ and HashJoin from day one | [§5 P4](../ROADMAP.md#p4--execution-engine-xl) | If P4 hardcodes "a join is a hash join", P8 becomes a rewrite rather than an addition |
| Rewrites only, no cost model | [§5 P4](../ROADMAP.md#p4--execution-engine-xl) | Cost needs statistics that do not exist until P8 |
| Everything addresses data by `RID`, never `PageRef` | [§3.1](../ROADMAP.md#31-where-the-layers-sit-after-p2) | An operator holding a `PageRef` means the layering leaked |
| A tuple span must not outlive its guard | [N5](../ROADMAP.md#n5--gettuple-hands-out-a-span-into-a-frame-that-can-be-evicted-underneath-it) | This is the phase where N5 stops being theoretical |

## The N5 hazard, stated once

[N5](../ROADMAP.md#n5--gettuple-hands-out-a-span-into-a-frame-that-can-be-evicted-underneath-it)
is harmless today because every P1 caller consumes its span before unpinning. **P4 is where
it fires.** A `Next()` up the pipeline can trigger a fetch, which can trigger an eviction,
which rewrites bytes a parent operator is still reading. Silent wrong data, non-deterministic,
only under memory pressure.

The rule for every operator in this phase: **`Next()` copies out of the guarded span before
returning, or returns the guard alongside it.** Never a bare span that outlives the call.
Item 4.1 pins this with a test, and it is worth re-checking at every operator.
